第九课：trait 与泛型——同一份契约，两种多态

本课路线：你已经用过 Option<T>、Result<T, E>、Vec<T>。今天把 <T> 从“用”翻到“定义”：先写 trait（契约），再用 <T: Trait> 让编译器为每个具体类型生成代码（静态分发），然后用 &dyn Trait / Box<dyn Trait> 把具体类型擦除（动态分发），最后用 Box<dyn Error> 收掉 errors5，并回收闭包的 Fn / FnMut / FnOnce。
判断标准：不再把 trait 说成“父类/接口继承”，能在 <T: Trait>、&dyn Trait、Box<dyn Trait>、自定义错误枚举之间选对工具。

本课示例均用 rustc 1.99.1（edition 2021）实测；英文原文与报错附中文对照。代码里的中文注释是给你看的，不需要抄进最终项目。

0. 两种多态，一个契约

多态（polymorphism）指的是“同一个接口，多种具体类型”。Rust 用 trait 写这个接口，但有两种使用方式：

  1. 静态分发（static dispatch）：写 fn describe<B: ButtonInput>(button: &B)。编译器在调用点就知道 B 是哪个具体类型，为每个具体类型生成一份特化代码。运行期不再查“这是哪个类型”。
  2. 动态分发（dynamic dispatch）：写 fn describe_dyn(button: &dyn ButtonInput)。具体类型被擦除，运行期通过函数表找到实现；同一份代码可以处理不同的具体类型，适合异构集合。

C 程序员的两个锚点（只是类比，不是同一机制）：

  • <T: Trait> ≈ 宏为每个具体类型展开一份调用代码；编译期就绑定好，运行期没有函数指针表。
  • &dyn Trait / Box<dyn Trait> ≈ C 的“结构体里放函数指针 + 一个 void* 上下文”；运行期查表调用。Rust 把这张表藏起来，并在编译期检查 trait 契约。

为什么现在讲：摇杆固件里，rp2040-hal 的引脚实现 embedded-hal 的 InputPin trait；驱动逻辑写成泛型，能同时服务真引脚和测试假引脚。到了 PC 端错误处理，又要用 Box<dyn Error> 把不同错误装进同一个返回类型。两种用法都绕不开 trait。

1. trait：把能力写成契约

1.1 两份一模一样的函数

假设有两个按键来源：真实引脚和测试用的假引脚。先看一个完整可运行的程序：不用 trait，各自写 inherent 方法，再写两份 describe。

// 两个按键来源：真实引脚、测试假引脚
struct RealPin {
    pin: u8,
}

struct FakePin {
    pressed: bool,
}

// 先不用 trait：各自写 inherent 方法
impl RealPin {
    fn is_pressed(&self) -> bool {
        self.pin == 15 // 模拟：引脚 15 按下
    }
}

impl FakePin {
    fn is_pressed(&self) -> bool {
        self.pressed
    }
}

// 两份函数体一模一样，只有参数类型不同
fn describe_real(pin: &RealPin) -> &'static str {
    if pin.is_pressed() { "pressed" } else { "released" }
}

fn describe_fake(pin: &FakePin) -> &'static str {
    if pin.is_pressed() { "pressed" } else { "released" }
}

fn main() {
    let real = RealPin { pin: 15 };
    let fake = FakePin { pressed: false };
    println!("real: {}", describe_real(&real));
    println!("fake: {}", describe_fake(&fake));
}

预期输出：

real: pressed
fake: released

这段程序在做什么：

  • RealPin / FakePin 各自保存自己的数据；impl RealPin / impl FakePin 给它们各自加了一个 inherent 方法。
  • describe_real 和 describe_fake 的函数体完全一样，只有参数类型不同。
  • main 创建两个值，分别调用两份函数；输出相同格式。

函数体一模一样，只有参数类型不同。C 里要么复制，要么用 void* + 函数指针；Rust 的选择是：先给这种能力起个名字，再让两个类型分别承诺实现它。

1.2 trait 定义与 impl

把上面两个 inherent impl 删掉，改成 trait 实现。下面是新的完整程序：

trait ButtonInput {
    fn is_pressed(&self) -> bool;
}

struct RealPin {
    pin: u8,
}

struct FakePin {
    pressed: bool,
}

impl ButtonInput for RealPin {
    fn is_pressed(&self) -> bool {
        // 真实硬件里这里读寄存器；课堂用引脚号模拟
        self.pin == 15
    }
}

impl ButtonInput for FakePin {
    fn is_pressed(&self) -> bool {
        self.pressed
    }
}

fn main() {
    let real = RealPin { pin: 15 };
    let fake = FakePin { pressed: false };
    println!("real: {}", real.is_pressed());
    println!("fake: {}", fake.is_pressed());
}

预期输出：

real: true
fake: false

两份 describe_* 函数已经删掉了；下一节用泛型只写一份。先记住这个 trait 版本的关键点：

  • trait 块只写方法签名；方法体写在各自的 impl 里。&self 表示只读借用；trait 方法也可以写 &mut self 或 self，接收者决定调用时是借用还是取得所有权。
  • trait 不能携带字段。数据（pin、pressed）留在具体类型里；trait 只描述“能做什么”。
  • trait 本身不是可以创建值的具体类型：不能写 let x: ButtonInput；有值的是具体类型 RealPin / FakePin。dyn ButtonInput 是 trait object 的类型，下一节讲。
  • impl Trait for Type 不是继承。它没有父类、没有字段继承，也不会让 RealPin 变成 ButtonInput 的子类型；它只是让 RealPin 满足这份契约。
  • 一个类型可以实现多个 trait；trait 之间也不构成类继承树。
  • Self 在 trait 里指实现它的具体类型；在 impl ButtonInput for RealPin 里，Self 就是 RealPin。
  • ButtonInput 是对象安全的：方法接收 &self、返回 bool，没有返回 Self、没有泛型参数；所以后面可以写 dyn ButtonInput。不是所有 trait 都能这样做，完整规则以后再说。
用例重锚：button 只是载体。原理是“任意具体类型都可以承诺同一组行为”；换成 Sensor、Pin、Transport，模式完全一样。不要把这个例子当成 trait 存在的原因。

2. 泛型 + bound：编译期特化

2.1 写一次，服务多种类型

有了契约，describe 可以只写一份。下面是完整程序（trait、结构体、impl、泛型函数、main 都在）：

trait ButtonInput {
    fn is_pressed(&self) -> bool;
}

struct RealPin { pin: u8 }
struct FakePin { pressed: bool }

impl ButtonInput for RealPin {
    fn is_pressed(&self) -> bool { self.pin == 15 }
}
impl ButtonInput for FakePin {
    fn is_pressed(&self) -> bool { self.pressed }
}

fn describe<B: ButtonInput>(button: &B) -> &'static str {
    if button.is_pressed() { "pressed" } else { "released" }
}

fn main() {
    let real = RealPin { pin: 15 };
    let fake = FakePin { pressed: false };
    println!("real: {}", describe(&real));
    println!("fake: {}", describe(&fake));
}

预期输出：

real: pressed
fake: released

逐行看关键部分：

  • fn describe<B: ButtonInput>：B 是类型参数（type parameter），调用时才填入具体类型。
  • : ButtonInput 是约束（bound）：告诉编译器“这个 B 保证实现了 ButtonInput”。
  • button: &B：参数是“指向某个 B 的引用”；B 的具体类型由调用点决定。
  • button.is_pressed()：能调用它，唯一依据就是 bound；bound 是编译期的能力清单，不是运行期检查。
  • main 里两次调用传入不同具体类型，触发两次单态化；下一节展开。

类型链：

describe(&real)
→ B = RealPin
→ &B = &RealPin
→ button.is_pressed() → RealPin::is_pressed

2.2 去掉 bound 会发生什么

把 2.1 完整程序里的签名只改一处：删掉 : ButtonInput。

// 其他代码不变，只改这一行
fn describe<B>(button: &B) -> &'static str {
    if button.is_pressed() { "pressed" } else { "released" }
}

重新编译，编译器在编译期就拒绝：

英文原文 
error[E0599]: no method named `is_pressed` found for reference `&B` in the current scope
help: items from traits can only be used if the type parameter is bounded by the trait
help: ... restrict type parameter `B` with trait `ButtonInput`
中文对照
  • 在当前作用域中，引用 &B 上找不到名为 is_pressed 的方法。
  • 只有类型参数被该 trait 约束时，才能使用 trait 中的项。
  • 考虑用 ButtonInput 约束类型参数 B。

注意错误编号是 E0599（方法找不到），不是 E0277（trait 约束不满足）。它的 help 已经把修法写出来了：加上 : ButtonInput。

2.3 单态化与静态分发

调用 describe(&real) 和 describe(&fake) 时，编译器看到两个不同的 B，通常会为每个具体类型生成一份特化代码。这叫单态化（monomorphization），对应静态分发（static dispatch）。

问题什么时候回答
B 是哪个具体类型？编译期（调用点）
B 有没有 is_pressed？编译期（bound 检查）
运行期调用哪份代码？已经确定，直接调用
  • 好处：运行期没有“查这是哪个类型”的步骤；调用点直接绑定，优化器容易内联。
  • 代价：每个具体类型一份代码，类型多了二进制会变大；所有具体类型必须在编译期已知。
  • 优化器可能把相同机器码合并；但语言层面的语义仍然是“按具体类型特化”，不是运行期分发。

3. trait object：运行期装箱

3.1 完整程序：&dyn 与 Box<dyn>

同一份契约，第二种用法是把具体类型擦掉。下面是一个完整程序：上半段用 &dyn，下半段用 Box<dyn>；先整体运行，再拆开看。

trait ButtonInput {
    fn is_pressed(&self) -> bool;
}

struct RealPin { pin: u8 }
struct FakePin { pressed: bool }

impl ButtonInput for RealPin {
    fn is_pressed(&self) -> bool { self.pin == 15 }
}
impl ButtonInput for FakePin {
    fn is_pressed(&self) -> bool { self.pressed }
}

fn describe_dyn(button: &dyn ButtonInput) -> &'static str {
    if button.is_pressed() { "pressed" } else { "released" }
}

fn main() {
    let real = RealPin { pin: 15 };
    let fake = FakePin { pressed: false };

    // 1) &dyn：借用的 trait object，可放不同具体类型
    let inputs: Vec<&dyn ButtonInput> = vec![&real, &fake];
    for input in inputs {
        println!("dyn: {}", describe_dyn(input));
    }

    // 2) Box<dyn>：拥有堆上的 trait object
    let boxed: Box<dyn ButtonInput> = Box::new(RealPin { pin: 3 });
    println!("boxed.is_pressed() = {}", boxed.is_pressed());
    println!("boxed describe = {}", describe_dyn(boxed.as_ref()));
}

预期输出：

dyn: pressed
dyn: released
boxed.is_pressed() = false
boxed describe = released

3.2 &dyn：借用一个 trait object

先看完整程序里的第一段：

let inputs: Vec<&dyn ButtonInput> = vec![&real, &fake];
for input in inputs {
    println!("dyn: {}", describe_dyn(input));
}

这是完整程序里的片段；real、fake、describe_dyn 都在上面定义。

  • dyn ButtonInput 读作“某个实现了 ButtonInput 的具体类型，但具体是谁运行期才知道”。这叫 trait object（trait 对象）。
  • dyn ButtonInput 是未定长（unsized）的，不能直接当局部变量；必须放在指针后面：&dyn ButtonInput 或 Box<dyn ButtonInput>。
  • &dyn ButtonInput 只借用，不拥有堆上的值；调用时通过函数表找到具体实现。
  • 异构集合：泛型函数的一个 B 只能是一个具体类型；Vec<B> 里不能同时放 RealPin 和 FakePin。但 Vec<&dyn ButtonInput> 可以；每个元素都是“数据指针 + 函数表指针”。

3.3 Box<dyn>：拥有一个 trait object

&dyn 借用，生命周期受外部值限制；需要拥有一个 trait object 时，用 Box<dyn Trait>。看完整程序的后半段：

let boxed: Box<dyn ButtonInput> = Box::new(RealPin { pin: 3 });
println!("boxed.is_pressed() = {}", boxed.is_pressed());
println!("boxed describe = {}", describe_dyn(boxed.as_ref()));

这是完整程序里的片段；ButtonInput、RealPin、describe_dyn 都在 3.1 定义。

  • Box::new(value) 把值放到堆上；Box 拥有它，离开作用域时通过 Drop 释放。你第一课学的所有权在这里照常生效。
  • Box<dyn ButtonInput> 是一个胖指针：一个数据指针 + 一个函数表指针；它指向堆上的具体值，但编译期不知道具体类型。
  • 编译期 vs 运行期：编译期确定 vtable、生成构造胖指针的代码；运行期执行到 coercion 点才组装数据指针 + vtable 指针。
  • 方法调用会自动解引用（boxed.is_pressed() 可以）；把 &Box<dyn T> 传给 &dyn T 参数时要显式解引用：boxed.as_ref() 或 &**boxed。
  • 尺寸（本机 x86_64 实测，不是跨平台语言保证）：Box<RealPin> 是 8 字节（细指针）；&dyn ButtonInput、Box<dyn ButtonInput>、&[u8] 都是 16 字节（胖指针）。第三课的切片是“地址 + 长度”，trait object 是“地址 + 函数表”。
类型大小说明
Box<RealPin>8具体类型，细指针
&dyn ButtonInput16借用 trait object，胖指针
Box<dyn ButtonInput>16拥有 trait object，胖指针
&[u8]16切片胖指针（第三课对照）

3.4 动态分发的代价与边界

  • 代价：每次调用要通过函数表找实现，通常比静态分发多一次间接跳转；也更难内联。换来的是“一份代码处理多种具体类型”和异构集合。
  • 对象安全：不是所有 trait 都能写成 dyn Trait。返回 Self、带泛型参数的方法、没有 self 的关联函数等，可能让 trait 不满足对象安全。ButtonInput 和 Error 都可以；完整规则以后再说。
  • C 锚点：&dyn Trait ≈ 一个 void* 数据指针 + 一张函数指针表；Rust 把这张表自动生成并检查类型。

4. 标准库 trait 与 Box<dyn Error>

你已经见过这些 trait，只是当时没点名。现在把它们放回 trait 的框架里。

4.1 Debug：调试打印

  • #[derive(Debug)] 让编译器生成 impl Debug for 类型；它不是魔法，只是自动写 impl。
  • {:?} 要求值的类型实现 Debug；Result::unwrap 要求错误类型 E: Debug（panic 时要打印错误）。
  • main -> Result<(), E> 也要求 E: Debug，因为 Result 的 Termination 实现需要它。第八课报过 E0277，今天知道它来自哪里。

你的 WoL 里：MacError 在 protocol.rs 顶部有 #[derive(Debug)]；main 在 main.rs 里返回 Result<(), MacError>。两者能配上，就是因为 MacError: Debug。

4.2 Display：面向用户的打印

{} 走 Display；{:?} 走 Debug。标准库的错误 trait 要求两者都有：

pub trait Error: Debug + Display {
    // 默认方法由标准库提供，实现者通常不用写
}

这叫 supertrait（超级 trait）：Error 的契约里写着 Debug + Display，所以实现 Error 之前必须先有这两个。上面是简化签名；errors5 的 CreationError 是 enum，下面是一个完整的对应程序：

use std::error::Error;
use std::fmt;

#[derive(Debug)]                 // 满足 Debug
enum CreationError {
    Negative,
    Zero,
}

impl fmt::Display for CreationError {   // 满足 Display
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        let description = match self {
            CreationError::Negative => "number is negative",
            CreationError::Zero => "number is zero",
        };
        f.write_str(description)
    }
}

impl Error for CreationError {}  // Debug + Display 已满足，空 impl 即可

fn main() {
    for e in [CreationError::Negative, CreationError::Zero] {
        println!("Display: {}", e);
        println!("Debug: {:?}", e);
    }
}

预期输出：

Display: number is negative
Debug: Negative
Display: number is zero
Debug: Zero
  • fmt::Formatter 是输出缓冲区，fmt::Result 是格式化结果；这段是标准库格式化的固定写法，errors5 已经提供，不需要你从零设计。
  • impl Error for CreationError {} 是空 impl：Error 的默认方法由标准库提供；只要 Debug + Display 已经满足，空 impl 就表示“承诺实现这份契约”。
  • 如果缺 Display，连 impl Error 都过不了。把上面的 impl fmt::Display 整段删掉，重新编译，实测报错：
英文原文 
error[E0277]: `CreationError` doesn't implement `std::fmt::Display`
help: the trait `std::fmt::Display` is not implemented for `CreationError`
note: required by a bound in `std::error::Error`
中文对照
  • CreationError 没有实现 std::fmt::Display。
  • std::error::Error 的约束要求实现者先满足 Display。

4.3 Error：所有错误的共同契约

  • Error 是标准库的错误 trait；ParseIntError 已经实现它，errors5 的 CreationError 通过 impl Error for CreationError {} 实现它。
  • Error 是对象安全的，所以可以写 Box<dyn Error>：一个能装下“任何实现了 Error 的错误”的盒子。
  • Box<dyn Error> 本身拥有堆上的错误值；它实现了 Debug（因为 Error: Debug），所以能作为 main 的返回错误。

4.4 From：? 背后的转换 trait

From 的方向很容易说反。假设 MacError 已经增加了一个 BadNumber(ParseIntError) 变体（errors6 会用同样的模式包 ParseIntError）。下面是一个完整程序：

use std::num::ParseIntError;

#[derive(Debug)]
enum MacError {
    // 真实 WoL 还有 Length / NonHex；这里只保留演示所需变体
    BadNumber(ParseIntError),
}

impl From<ParseIntError> for MacError {
    fn from(e: ParseIntError) -> Self {
        MacError::BadNumber(e)
    }
}

fn parse_byte(s: &str) -> Result<u8, MacError> {
    let n = s.parse::<u8>()?; // 失败时 ParseIntError -> MacError
    Ok(n)
}

fn main() {
    println!("{:?}", parse_byte("255")); // Ok(255)

    match parse_byte("FF") {
        Ok(n) => println!("Ok({n})"),
        // "FF" 默认按十进制 parse，会得到 InvalidDigit
        Err(MacError::BadNumber(e)) => println!("BadNumber({:?})", e.kind()),
    }
}

预期输出：

Ok(255)
BadNumber(InvalidDigit)

这表示 ParseIntError → MacError。当函数的返回错误是 MacError，而 ? 拿到的是 ParseIntError 时，? 会执行 return Err(MacError::from(e))。转换不了就是编译期错误，不是运行期失败。

对照你现在的 WoL：parse_mac 在 protocol.rs 里用的是 u8::from_str_radix(part, 16).map_err(|_| MacError::NonHex)?；完整函数见项目文件，这里不贴半截代码。

map_err 是手动转换：在调用点把 ParseIntError 变成 MacError::NonHex，然后 ? 看到的已经是同一种错误类型。它简单、能选择变体，但每处都要写。From 是集中转换：实现一次，? 自动调用。errors6 会让你把 ParseIntError 包进自定义错误的一个变体里，既保留原因，又能在 From 或 map_err 里集中转换。

4.5 Termination：main 的返回类型

main 的返回类型必须实现 Termination。() 实现了；Result<(), E> 在 E: Debug 时也实现了。于是：

  • Ok(())：程序正常结束，退出码 0。
  • Err(e)：运行期用 Debug 打印 Error: {e:?}，退出码 1。
  • Box<dyn Error> 是 Debug，所以 Result<(), Box<dyn Error>> 满足 Termination。这就是 errors5 的 main 能直接返回它的原因。

4.6 errors5 的完整模式

把上面的东西拼起来，得到一个完整程序（PositiveNonzeroInteger 的类型定义也在里面）：

use std::error::Error;
use std::fmt;

#[derive(Debug)]
enum CreationError {
    Negative,
    Zero,
}

impl fmt::Display for CreationError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        let description = match self {
            CreationError::Negative => "number is negative",
            CreationError::Zero => "number is zero",
        };
        f.write_str(description)
    }
}

impl Error for CreationError {}

#[allow(dead_code)] // 单独运行时字段只用于 Debug；errors5 的测试会读它
#[derive(Debug)]
struct PositiveNonzeroInteger(u64);

impl PositiveNonzeroInteger {
    fn new(value: i64) -> Result<Self, CreationError> {
        match value {
            x if x < 0 => Err(CreationError::Negative),
            0 => Err(CreationError::Zero),
            x => Ok(Self(x as u64)),
        }
    }
}

fn main() -> Result<(), Box<dyn Error>> {
    let input = "42"; // 改成 "-5" 或 "abc" 复现另外两行
    let x: i64 = input.parse()?;
    println!("output={:?}", PositiveNonzeroInteger::new(x)?);
    Ok(())
}

用 input = "42" 运行，预期输出：

output=PositiveNonzeroInteger(42)
exit=0
  • input.parse::<i64>() 失败时产生 ParseIntError；? 通过标准库的 From<E> for Box<dyn Error> 把它装箱。
  • PositiveNonzeroInteger::new(x) 失败时产生 CreationError；它已经实现 Display 和 Error，所以 ? 也能装箱。
  • 两种错误类型完全不同，但都被擦除成 Box<dyn Error>，main 只写一个返回类型。

实测三种输入的输出（errors5 的代码结构，输入换成参数）：

注意 -5 打印的是 Error: Negative（Debug），不是 Display 的 "number is negative"。main 的错误打印走 Debug；Display 是给你自己用 {} 打印用户消息时准备的。这就是为什么 Error 两个都要。

什么时候用 Box<dyn Error>：应用层的 main 想快速统一多种错误，可以。库代码（比如你的 parse_mac）优先用自定义错误枚举：调用者能按 Length / NonHex 做决策，而不是拿到一个只能打印的盒子。固件 no_std 没有堆分配器，Box 用不了，更要用自定义错误。errors6 的注释说的就是这件事。

5. 闭包的三张门牌：Fn / FnMut / FnOnce

第四课写闭包时见过 Fn / FnMut / FnOnce，当时只当作“门牌”。现在有了 trait，可以正式回收：它们就是标准库描述“闭包怎么使用捕获环境”的三个 trait。

trait调用时的接收者能不能改捕获值能调用几次
Fn&self不能多次
FnMut&mut self能多次
FnOnceself消费捕获值一次

关系是 Fn: FnMut、FnMut: FnOnce：能当 Fn 用的闭包，也能当 FnMut 和 FnOnce 用；反过来不成立。这和 Error: Debug + Display 是同一种 supertrait 结构。

5.1 先只玩闭包：定义、捕获、调用

先不看泛型，只把一个计数器闭包跑起来。注意：定义闭包时闭包体不执行。

fn main() {
    let mut n: u32 = 0;          // n 可变，初始 0
    let mut inc = || {           // 定义闭包；此时不执行
        n += 1;                  // 调用时：修改捕获的 n
        n                        // 尾表达式：返回加完后的 n
    };

    println!("first: {}", inc());   // 1
    println!("second: {}", inc());  // 2
    println!("n = {n}");            // 2
}

预期输出：

first: 1
second: 2
n = 2
  • || 是空参数列表；闭包体是一个代码块，可以有语句和尾表达式。
  • n += 1; 是语句，分号把它的值（()）丢掉；最后的 n 没有分号，是尾表达式，它的值就是闭包的返回值。写成 n; 就返回 () 了。
  • 闭包修改了捕获的 n，所以按可变借用捕获 n，不是复制。调用 inc() 改的是外面的 n。
  • 定义 inc 时闭包体不执行，n 还是 0；只有调用 inc() 才执行。
  • 两个 mut 各管各的：mut n 让闭包能改 n；mut inc 让调用者能可变借用闭包。
  • inc 的类型不是 u32，而是一个匿名闭包类型，实现 FnMut() -> u32（也实现 FnOnce）。
步骤ninc() 返回
let mut n = 00—
let mut inc = ...0—（定义不执行）
第一次 inc()11
第二次 inc()22
println!("n = {n}")2—

5.2 Fn：不修改捕获，先看懂泛型 call_twice

先用一个不修改捕获的闭包，把 call_twice 的泛型签名和元组返回拆开：

fn call_twice<F: Fn() -> u32>(f: F) -> (u32, u32) {
    let first = f();     // 第一次调用
    let second = f();    // 第二次调用
    (first, second)      // 返回元组
}

fn main() {
    let f = || 7;                 // 没有捕获，实现 Fn
    let pair = call_twice(f);
    println!("{pair:?}");         // (7, 7)
}

预期输出：

(7, 7)
  • <F: Fn() -> u32>：F 是类型参数；约束读作“F 可被 &self 调用，没有参数，返回 u32”。
  • f: F：这里没有 mut，因为 Fn 调用只需要 &self。
  • -> (u32, u32)：返回一个二元组；(first, second) 是元组表达式，不是函数调用。
  • 为什么写 let first / let second：把执行顺序拆开，先第一次，再第二次；不要用一行元组隐藏步骤。

5.3 FnMut：修改捕获，多次调用

现在把计数器闭包传给需要 FnMut 的 call_twice：

fn call_twice<F: FnMut() -> u32>(mut f: F) -> (u32, u32) {
    let first = f();     // n 0 -> 1，返回 1
    let second = f();    // n 1 -> 2，返回 2
    (first, second)
}

fn main() {
    let mut n: u32 = 0;
    let mut inc = || {
        n += 1;
        n
    };

    let pair = call_twice(&mut inc);
    println!("pair = {pair:?}");          // (1, 2)
    println!("inc() again = {}", inc());   // 3
}

预期输出：

pair = (1, 2)
inc() again = 3
  • 为什么 mut f：FnMut 调用需要 &mut self；f 是函数持有的闭包（这里是 &mut inc），必须声明为可变。
  • 为什么 mut inc：闭包捕获 n 并会修改；调用点必须能可变借用这个闭包。
  • 为什么 &mut inc：call_twice 按值接收 F；传 &mut inc 让 F = &mut 闭包，函数借用它，返回后 inc 仍可用。传 inc 会把闭包移动进去，之后不能再用 inc（E0382）。
  • 两个 mut 不是重复：一个在调用者（inc），一个在被调用函数（f）。
  • 原课件把函数体写成 (f(), f())；这里展开成 let first / let second，执行顺序一眼可见。

5.4 FnOnce：消费捕获值，只能调用一次

fn consume<F: FnOnce() -> String>(f: F) -> String {
    f()
}

fn main() {
    let s = String::from("hi");
    let take = move || s;            // 把 s move 进闭包
    println!("{}", consume(take));   // hi
    // println!("{}", consume(take)); // E0382：take 已经被移走
}

预期输出：

hi
  • move || s 把 String 的所有权移进闭包；调用 f() 时闭包被消费，所以它只保证一次调用，是 FnOnce。
  • 如果闭包只读捕获值，它可以实现 Fn；如果修改，至少是 FnMut；如果消费，只能是 FnOnce。
  • 第二次 consume(take) 会报 E0382：take 已经被移走。

C 锚点：C 的函数指针没有捕获环境；闭包相当于“函数指针 + 捕获的环境”。Fn / FnMut / FnOnce 描述调用时对这份环境是只读、可改，还是拿走所有权。

6. 收束：怎么选

需求选择
具体类型编译期已知；性能优先；同一种类型批量处理<T: Trait>，静态分发，单态化
需要装不同具体类型；运行期统一处理；异构集合&dyn Trait（借用）或 Box<dyn Trait>（拥有）
应用层想快速统一多种错误；main 返回Box<dyn Error>
库代码要按错误种类做决策；固件 no_std 无堆自定义错误枚举（如 MacError）

三句话总结：

  1. trait 是行为契约；impl Trait for Type 提供行为，不提供字段，也不是继承。
  2. <T: Trait> 编译期特化，运行期零查表；&dyn / Box<dyn> 运行期查表，能装异构类型。
  3. Box<dyn Error> 是应用层统一错误的工具；库和固件优先自定义错误枚举。

常见误区：

  • “trait 是父类/接口继承” → trait 是契约；impl 不继承字段，Rust 没有类继承。
  • “<T> 是运行期类型参数” → 它是编译期类型参数，单态化后运行期没有类型分发。
  • “bound 是运行期检查” → 它是编译期门禁；没有 bound 直接 E0599。
  • “Box<dyn Trait> 自动实现 Trait” → 它是胖指针；传给 &dyn Trait 要 as_ref() 或 &**，方法调用才会自动解引用。
  • “main -> Result 的错误打印用 Display” → 用 Debug；Display 是 {} 的用户消息。
  • “Box<dyn Error> 到哪都好” → 库代码要可匹配的错误类型；no_std 没堆，用不了 Box。

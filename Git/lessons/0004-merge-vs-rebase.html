第四课：merge 还是 rebase——把分叉讲清楚

这一课只拿一个东西：看到两条分支分叉时，能画出 fast-forward、merge、rebase 三种结果，并说清楚「谁会改写历史、谁适合共享分支」。

1. 分叉不是错误，是并行工作的正常形状

第一课说过，分支只是指向提交的指针。两个人（或两个任务）从同一个提交出发，各自往前提交，历史就分叉了：两条链共享一个共同祖先（common ancestor），之后各走各的。

分叉之后，要把两条线合到一起，Git 给你两种基本动作：merge（合并）和 rebase（变基）。它们不是「高级/低级」之分，而是对历史的两种态度：

mergerebase
对历史保留分叉，增加一个合并点把提交搬到新基底，拉成直线
提交哈希已有提交不变被重放的提交全部换新哈希
适合共享分支、想保留真实协作痕迹个人分支、推送前整理历史

2. fast-forward：没有分叉时，连合并提交都不用

如果 main 是 feature 的祖先——也就是说，main 停在分叉点上没动，只有 feature 在前进——那么把 feature 合进 main 只需要把 main 指针往前挪。没有分叉，也就不需要合并提交。这叫 fast-forward（快进）。

git switch main
git merge feature
# Fast-forward
#  main 直接前移到 feature 的位置

想强制要求「必须能快进，否则报错」，用 git merge --ff-only feature。反过来，即使能快进也想留下一个合并提交，用 git merge --no-ff feature。

3. merge：生成一个双亲提交

两边都有新提交时，merge 会创建一个新的 merge commit：它的父提交有两个——一个是 main 的最新提交，一个是 feature 的最新提交。历史保留分叉，像两条河在一个点汇合。

git switch main
git merge feature -m "merge: 合并 feature"
# 生成 m，父提交是 main 的 c3 与 feature 的 f2

merge 不会改写任何已有提交，所以对已经推送、别人可能在用的分支是安全的。代价是历史不再是直线，读 git log --graph 时能看到分叉与汇合。

4. rebase：把你的提交「重放」到新基底上

rebase 的思路不同：它找到两条分支的共同祖先，把你这一侧独有的提交逐个重放到目标分支的最新提交之后。每个重放出来的提交内容相似，但父提交变了，所以哈希全变。

git switch feature
git rebase main
# 把 feature 上独有的提交重放到 main 的最新提交之后

结果是一条直线，像你一开始就从最新的 main 拉出分支一样。原来的提交并没有立刻被删除——它们还躺在 reflog 里一段时间——但分支已经不再指向它们。对协作者来说，这段历史被改写了。

冲突时：rebase 会停在冲突处。解决文件后 git add <文件>，再 git rebase --continue；想放弃就 git rebase --abort。不要用 git commit 去「完成」一次 rebase——那会打乱重放流程。

6. 金色法则：别 rebase 别人脚下的历史

Pro Git 的原话：“Do not rebase commits that exist outside your repository and that people may have based work on.”
中文：不要对「已经存在于你的仓库之外、且别人可能基于它工作」的提交执行变基。

原因很直接：rebase 会换掉提交的哈希。别人基于旧提交继续工作，你再把改写后的历史推上去，对方的历史就对不上了——轻则重复提交，重则冲突一片。判断标准不是「分支有没有推送过」，而是「有没有别人可能已经基于这些提交工作」。

  • 个人 feature 分支、还没推送：放心 rebase 整理历史。
  • 已经推送、只有你用的 feature 分支：可以 rebase，但推送时需要 --force-with-lease；先确认没有别人参与。
  • main / 共享分支：不要 rebase。用 merge，或通过 Pull Request 合并。

7. 怎么选：一张决策表

场景选择理由

8. 沙箱练习：各做一次 merge 与 rebase

沙箱没搭好时，先在 Git/ 目录运行 bash git_sandbox.sh。--reset 会删除 sandbox 内容，确认不需要保留旧练习再用。

merge：制造分叉，再汇合

cd Git/sandbox/work
git switch main

# 从 main 拉出 merge-demo，提交一次
git switch -c merge-demo
echo "merge 演示" >> notes.md
git add notes.md
git commit -m "docs: merge 演示提交"

# 回到 main，也提交一次（制造分叉）
git switch main
echo "main 前进" >> README.md
git add README.md
git commit -m "docs: main 前进"

git log --oneline --graph --all

# 合并，并直接给出提交信息，避免打开编辑器
git merge merge-demo -m "merge: 合并 merge-demo"

git log --oneline --graph --all
# 应看到一个 merge commit，父提交有两条线

rebase：把提交搬到新基底

# 从 main 拉出 rebase-demo，提交一次，记下哈希
git switch -c rebase-demo
echo "rebase 演示" >> notes.md
git add notes.md
git commit -m "docs: rebase 演示提交"
git log --oneline -1

# main 再前进一次
git switch main
echo "main 又前进" >> README.md
git add README.md
git commit -m "docs: main 又前进"

# 回到 rebase-demo，重放到 main 之后
git switch rebase-demo
git rebase main

git log --oneline -1          # 哈希变了
git log --oneline --graph --all
# 应是一条直线，rebase-demo 接在 main 之后

要观察的：merge 之后历史有分叉与汇合点；rebase 之后你的提交换了哈希，但历史是一条直线。两种操作都保留了你和 main 的改动，只是讲述方式不同。

思考题：如果 rebase-demo 已经推送到远程，再执行上面的 rebase，下一次 push 会发生什么？答案在第三课：远端有旧提交，你的新历史不是它的后代，于是 non-fast-forward。只有独占分支才考虑 --force-with-lease。

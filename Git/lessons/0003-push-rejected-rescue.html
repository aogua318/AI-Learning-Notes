第三课：推送被拒急救——non-fast-forward

这一课只拿一个东西：看到 ! [rejected] ... (fetch first) 不再慌，能按「fetch → 看分叉 → 选 rebase 或 merge → 再 push」四步走完，并且知道为什么不该顺手 --force。

1. 报错长什么样

最常见的一版是这样（哈希、分支名会不同）：

To github.com:you/AI-Learning-Notes.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:you/AI-Learning-Notes.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.

另一版会写 (non-fast-forward)。两者说的是同一件事：远端的 main 上有你本地历史里没有的提交。如果 Git 接受了这次推送，那些提交就会从 main 的历史里消失——所以它拒绝覆盖，让你先合并。

这不是权限问题，也不是网络问题。它恰恰是 Git 在保护协作历史。真正要检查的是：远端多了什么？我本地多了什么？

2. 先诊断，别急着动手

# 第一步永远是取回远程的新位置，但不动你的工作区
git fetch origin

# 第二步：看领先/落后
git status -sb
# ## main...origin/main [ahead 1, behind 1]

# 第三步：看两条历史在哪里分叉
git log --oneline --graph --decorate --all

把结果归到下面三种情况，处理方式完全不同：

status 显示含义首选动作
只有 behind N你没有任何新提交，只是落后git pull --ff-only，然后 push
ahead 1, behind 1两边各有新提交，历史分叉git pull --rebase 或 git pull --no-rebase
你刚 amend / rebase 过你主动改写了本地历史只有在你独占的分支上，才考虑 --force-with-lease
别在没 fetch 的时候猜。git status 里的 origin/main 可能已经过时；先 fetch，地图才是新的。

3. 两条正路：rebase 还是 merge

路线 A：git pull --rebase（个人分支、想保持线性）

它先 fetch，再把你本地独有的提交逐个「重放」到 origin/main 的最新提交之后。结果是一条直线，但你的本地提交会换新哈希——因为父提交变了。

git pull --rebase
# 如果一路顺利：
git push

# 如果同一处被两边修改，会停在冲突：
git status                  # 看 both modified 的文件
# 手工编辑，删掉 <<<<<<< / ======= / >>>>>>> 标记
git add <解决后的文件>
git rebase --continue

# 不想继续了，回到 rebase 之前
git rebase --abort

路线 B：git pull --no-rebase（共享分支、想保留真实分叉）

它先 fetch，再把你本地 main 与 origin/main 合并，生成一个双亲的 merge commit。历史会分叉再汇合，但没有改写任何已有提交，适合多人共用的分支。

git pull --no-rebase
# 冲突时同样手工解决，然后：
git add <解决后的文件>
git commit                  # 完成这次 merge

# 放弃这次 merge
git merge --abort
pull --rebasepull --no-rebase
历史形状一条直线保留分叉 + 合并点
是否改写本地提交是，哈希会变否
适合尚未推送的个人提交已共享的分支
风险重放已共享的提交会害到别人历史多一个合并节点

4. 为什么不要顺手 --force

git push --force 的意思是「别检查祖先关系，直接用我的覆盖远端」。它会把远端 main 指向你的提交，别人已经推送、你本地没有的提交就从分支历史上掉下去了。即使对象还能在 reflog 里找到一段时间，对协作者来说历史已经被改写。

--force-with-lease 多做一道检查：远端的当前值是否仍等于我上次 fetch 时看到的值。如果这期间别人又推了新提交，它会拒绝，避免你把人家的提交一起覆盖。但它仍然是在改写历史——只适用于你独占的功能分支。

# 只在「这个分支只有我在用」且「确实需要改写历史」时
git push --force-with-lease

# 绝不要对 main / 共享分支这么做
# git push --force origin main   ← 不要
--force-with-lease 不是免死金牌。它防的是「你 fetch 之后别人又推了」；它不防「你不看历史就强推」。强推前先用 git log --graph --all 确认远端没有你要保留的提交。

6. 沙箱练习：亲手制造一次拒绝，再救回来

沙箱没搭好时，先在 Git/ 目录运行 bash git_sandbox.sh。--reset 会删除 sandbox 内容，确认不需要保留旧练习再用。

先扮演「队友」：另克隆一份远程仓库，提交并推送。

cd Git/sandbox
git clone remote.git other
cd other
git config user.name "teammate"
git config user.email "teammate@sandbox.local"
echo "队友的修改" >> README.md
git add README.md
git commit -m "docs: 队友更新 README"
git push origin main

如果 other 已存在，直接 cd other && git pull，不要重复 clone。

再回到你的工作仓库，制造分叉并推送：

cd ../work
git switch main
git push -u origin main        # 若还没设上游，先推一次

echo "我的修改" >> notes.md
git add notes.md
git commit -m "docs: 我的本地修改"

git push
# 预期：! [rejected] main -> main (fetch first) / non-fast-forward

现在走急救四步：

# 1. 取回远程的新位置（不动工作区）
git fetch origin

# 2. 看分叉：ahead 1, behind 1
git status -sb
git log --oneline --graph --decorate --all

# 3. 把你的提交重放到队友的提交之后
git pull --rebase

# 4. 再推
git push
git status -sb                 # 干净
git log --oneline --graph --decorate --all   # 一条直线

要观察的：第 2 步里 main 与 origin/main 各有一个对方没有的提交；第 3 步后，你的提交换了新哈希，接在队友的提交之后；第 4 步成功。这就是「先整合、再推送」。

换一种走法：把第 3 步改成 git pull --no-rebase，你会得到一个 merge commit，历史保留分叉。两种都正确，区别在「你想要直线，还是想保留真实合并」。第四课展开。

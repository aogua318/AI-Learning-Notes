Git 状态与引用：五组图看懂

这份参考页把 Git 里最容易混的几件事画成图：东西放在哪（工作区、暂存区、本地仓库、远程）、指针指向谁（HEAD、main、origin/main）、以及 失败之后怎么退。每张图都可以点击放大，图下方的命令是当前状态对应的最小操作集。

怎么用：先在图里找到你现在的状态，再读下面的命令，最后去 sandbox 里动手。图只负责帮你判断「现在在哪、下一步会改哪一层」；熟练度来自实际操作，不来自背图。

图例：本地提交远程提交HEAD / 危险操作已不在当前分支上的提交

看图要点：git add 写暂存区；git commit 写本地 .git；git push 才写远程。git fetch 只更新本地缓存的 origin/main，工作区一个文件都不动；git pull 才会碰工作区。

撤销也按图层分：git restore 把文件写回工作区；git restore --staged 只把改动撤出暂存区，文件内容不变；git reset / git revert 见第 ⑤ 页。

对应 README：0.2 三个区域、4.3 fetch vs pull vs push。

看图要点：HEAD 指向当前分支（通常）；main 指向本地最新提交；origin/main 指向「上次 fetch 时远程 main 的位置」。

最容易误会：以为 origin/main 就是 GitHub 的实时状态。不是。它只是本地缓存；同事推了新提交后，你不 fetch，本地根本不知道。

对应 README：0.4 本地仓库 vs 远程仓库、4.2 远程跟踪分支与 -u。

三步：git fetch 看清远程有什么 → git pull --rebase 把你的提交重放到最新提交之后 → git push。

不要条件反射：不要用 --force 把远程的 C 抹掉。确需强推自己的分支时用 git push --force-with-lease；共享分支永远不要强推。

对应 README：4.4 为什么会被拒绝、9.1 push 相关。

怎么选：merge 保留完整分叉，适合共享分支和想留下「这里发生过合并」的场景；rebase 让历史线性、干净，适合整理自己尚未推送的提交。

黄金法则：已经 push 到共享分支的提交，不要 rebase。确需强推自己的分支时用 --force-with-lease，不要用裸 --force。

对应 README：3.2 合并的三种结局、3.4 rebase 与它的黄金法则。

未推送：可以用 reset 整理本地历史。--soft 保留改动在暂存区，--mixed 留在工作区，--hard 直接丢弃——先确认没有想保留的改动。

已推送：一律用 revert。它追加一个新提交，不改变别人已经拿到的历史；reset 后强推会打乱协作者。

对应 README：第 2 章撤销操作、9.1 push 相关。

命令落在哪一层

命令 读 / 写哪一层 改历史？ 典型用途
git add 工作区 → 暂存区 否 挑选下一次 commit 的内容
git commit 暂存区 → 本地仓库 追加 建立存档点
git push 本地仓库 → 远程仓库 不改本地历史 上传提交；只接受快进
git fetch 远程 → 本地 origin/* 否 更新远程地图，不碰工作区
git pull 远程 → 本地分支 + 工作区 merge 可能新增合并提交；rebase 会改写本地未推送提交 同步并整合远程变化
git restore 暂存区 / HEAD → 工作区 否 撤销未提交的文件改动
git restore --staged HEAD → 暂存区 否 把改动撤出暂存区，文件内容不变
git reset 本地分支指针 + 暂存区 / 工作区 是（本地） 撤销未推送提交；三种模式决定改动去向
git revert 本地分支（追加新提交） 追加 撤销已推送提交；历史不改写

README 第 12 章 有完整剧本：首推、推分支、模拟同事、撞上 non-fast-forward、pull --rebase 自救。

被拒时的口诀

fetch → 看 → pull --rebase → push。不要用 --force 覆盖别人的提交。

已推送的撤销

用 revert，不要用 reset + 强推。前者追加历史，后者改写历史。

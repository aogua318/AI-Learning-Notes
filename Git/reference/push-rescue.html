推送急救卡

看到 ! [rejected] 时，按这张卡走。核心只有一句：先取回地图，再决定整合方式，最后才推送。不要一上来就 --force。

0. 先做这三条

git fetch origin
git status -sb
git log --oneline --graph --decorate --all

第一条刷新 origin/main 这张地图，第二条告诉你领先/落后，第三条让你看清分叉在哪里。看清之后再选路线。

求稳：动手前先固定当前位置——git branch backup-before-rescue。它不会改变任何提交，只是多一个引用；万一整合乱了，还能回到这里。

1. 按 status 选路线

git status -sb 显示含义下一步
[behind 2] 你只是落后，没有本地新提交 git pull --ff-only → git push
[ahead 1] 远程没变，只是你还没推 git push
[ahead 1, behind 2] 两边各有新提交，历史分叉 路线 A（rebase）或路线 B（merge）
你刚 amend / rebase 过 你主动改写了本地历史 路线 C（仅限自己独占的分支）
远端提示 protected branch 分支受保护，禁止强推/直推 新建分支 → 推送 → 开 Pull Request

2. 四条路线

A · 只落后：快进

git pull --ff-only

git push

不能快进就说明其实分叉了，换 B 或 C。

B · 分叉、想线性：rebase

git pull --rebase

冲突：改文件 → git add → git rebase --continue

git push

放弃：git rebase --abort

C · 分叉、想保留真实历史：merge

git pull --no-rebase

冲突：改文件 → git add → git commit

git push

放弃：git merge --abort

D · 自己分支改写历史：带租约强推

git push --force-with-lease

只用于你独占、没有别人参与的分支；强推前先看 git log --graph --all。

为什么默认不走 D：--force 会覆盖远程，可能抹掉别人已推送的提交；--force-with-lease 虽然多一道检查，但仍然在改写历史。main 和共享分支永远不要强推。

3. 冲突处理（rebase 与 merge 通用）

git status                  # 找到 both modified 的文件
# 打开文件，手工合并，删掉全部冲突标记：
#   <<<<<<< HEAD
#   =======
#   >>>>>>> 分支名
git add <解决后的文件>

# rebase 中：
git rebase --continue
# merge 中：
git commit

# 想放弃这次整合：
git rebase --abort         # 或
git merge --abort

冲突标记必须全部删除，包括行首的七个尖括号；只删一半也会被当成普通文本提交。解决后先跑测试或打开文件确认，再 git add。

4. 报错解码

报错片段含义动作
! [rejected] ... (fetch first) 你的地图过期，远端可能已有新提交 先 git fetch，再看 status
! [rejected] ... (non-fast-forward) 你的新位置不是远端当前位置的后代 路线 A/B/C，不要直接 force
! [rejected] ... (stale info) --force-with-lease 发现远端在你 fetch 后又变了 重新 fetch，确认远端内容后再决定
[remote rejected] ... (protected branch) 分支受保护，平台拒绝直推/强推 推送新分支，开 Pull Request
src refspec main does not match any 本地没有名为 main 的分支，或还没提交 git branch -vv 确认分支名与提交
Permission denied (publickey) SSH 认证失败，不是历史冲突 检查 SSH key / ssh -T git@github.com
Authentication failed HTTPS 凭据或 PAT 失效 更新凭据；GitHub 不再接受账户密码

5. 绝对不要

  • 不要对 main 或共享分支执行 git push --force。
  • 不要在没看 git log --graph --all 前强推——你可能正在覆盖别人的提交。
  • 不要用 git reset --hard 「修复」推送被拒；它会把未提交改动一起清掉。
  • 不要一遇到问题就删掉 .git/ 或重新 clone；多数情况本地提交还能救。
  • 不要用 git checkout -- . 清冲突；那会丢弃你正在解决的改动。

6. 三条安全习惯

推送前

git fetch → git status -sb。先知道自己在哪，再推。

动手前

git branch backup-日期 固定当前位置；出问题可回。

协作时

功能分支推送 → Pull Request → main。不要几个人直接往 main 推。
